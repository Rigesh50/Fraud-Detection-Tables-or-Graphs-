# Synthetic fraud-detection dataset — 1,100,000 nodes

Generated by `scripts/generate_fraud_data.py` (seed 42, so it is reproducible).
The shape is measured from the real `frauddetection` graph
([neo4j-graph-examples/fraud-detection](https://github.com/neo4j-graph-examples/fraud-detection),
a PaySim simulation, 332,973 nodes / 980,098 relationships) and reproduced at
3.30× that size.

```bash
python3 scripts/generate_fraud_data.py --nodes 1100000 --out fraud_1_1m --schema fraud_1_1m
```

| | Real dump | This dataset |
| --- | --- | --- |
| nodes | 332,973 | **1,100,000** |
| relationships | 980,098 | **3,238,159** |
| transactions | 323,489 | 1,068,669 |
| clients (of which mules) | 2,433 (433) | 8,038 (1,431) |
| merchants / banks | 347 / 3 | 1,146 / 10 |
| SSN / Email / Phone | 2,238 / 2,229 / 2,234 | 7,393 / 7,364 / 7,380 |
| CSV on disk | — | 89 MB |

## The graph

```
(:Client)-[:PERFORMED]->(:Transaction)          one performer per transaction
(:Transaction)-[:TO]->(:Merchant|:Client|:Bank) exactly one target
(:Transaction)-[:NEXT]->(:Transaction)          one chain per client, in globalStep order
(:Client)-[:FIRST_TX|LAST_TX]->(:Transaction)   the ends of that chain
(:Client)-[:HAS_SSN]->(:SSN)                    shared between clients
(:Client)-[:HAS_EMAIL]->(:Email)                shared between clients
(:Client)-[:HAS_PHONE]->(:Phone)                shared between clients
```

Nodes carry two labels where the real data does: every transaction is
`:Transaction` plus one of `:CashIn` `:CashOut` `:Payment` `:Transfer`
`:Debit`, and a fraudulent account is `:Client:Mule`.

| Transaction type | Count | Share | Goes to | Mean amount |
| --- | --- | --- | --- | --- |
| CashIn | 492,356 | 46.1% | Merchant | 139,493 |
| CashOut | 251,147 | 23.5% | Merchant | 126,503 |
| Payment | 246,370 | 23.1% | Merchant | 8,756 |
| Transfer | 64,287 | 6.0% | Client (12% of them a Mule) | 846,722 |
| Debit | 14,509 | 1.4% | Bank | 5,875 |

## What the generator reproduces

Not uniform random — the fraud signal has to survive the scale-up, or the
dataset is useless for testing fraud queries:

- **Fraud only where the real data has it.** `Transfer` at 3.59% and `Payment`
  at 0.26%; `CashIn`, `CashOut` and `Debit` are never fraudulent.
- **Every fraudulent Transfer goes to a Mule** (2,302 of them), and every
  fraudulent Payment goes to a Merchant (656) — exactly the real pattern.
- **Identities are shared between clients.** 8,038 clients hold only 7,393
  SSNs, 7,364 emails and 7,380 phones. One SSN is shared by 21 clients, another
  by 12, then 9, 8, 8 — the rings that fraud-detection queries hunt for.
  3,935 clients sit one shared identifier away from a mule.
- **Client activity is power-law skewed**, ~133 transactions each on average
  with a long tail, so index lookups and traversals vary in cost the way they
  do in the real data.
- **17.8% of clients are mules**, as in the source.

## Loading

### MySQL (schema `fraud_1_1m`) — 27 seconds

`LOAD DATA LOCAL INFILE` must be enabled on both sides:

The CSV paths in the loader are relative to this directory, so run it from
here — `LOAD DATA LOCAL INFILE` resolves them against the client's working
directory, not the server's.

```bash
cd fraud_1_1m
mysql -u root -p -e "SET GLOBAL local_infile=1;"
mysql --local-infile=1 -u root -p < load_mysql.sql
mysql -u root -p -e "SET GLOBAL local_infile=0;"
```

The script creates the schema, seven tables, ten foreign keys and the indexes.

The relational mapping, since the graph has shapes SQL has to spell out
differently:

```
banks(id PK, name)                merchants(id PK, name)
ssns(ssn PK)                      emails(email PK)      phones(phone_number PK)
clients(id PK, name, is_mule, ssn FK, email FK, phone_number FK,
        first_tx_id FK->transactions, last_tx_id FK->transactions)
transactions(id PK, type ENUM, amount, fraud, step, global_step, ts,
             client_id FK->clients,            -- PERFORMED
             to_merchant_id FK->merchants,     -- exactly one of these three
             to_client_id   FK->clients,
             to_bank_id     FK->banks,
             next_transaction_id FK->transactions)  -- NEXT, self-referencing
```

- The `:Mule` label becomes `clients.is_mule`, and the transaction subtype label
  becomes `transactions.type`.
- `TO` is polymorphic in the graph, so it needs three nullable foreign keys;
  exactly one is set per row (verified after loading).
- `clients` ↔ `transactions` reference each other, so the load runs with
  `FOREIGN_KEY_CHECKS=0` and the `first_tx`/`last_tx` constraints are added
  after both tables exist. Verify with the orphan queries below.

### Memgraph — 13-18 seconds, 1.58 GiB resident

Measured on Colima (4 CPU / 8 GiB, virtiofs); Docker Desktop behaves the same.
**Give the VM at least 4 GB** — the graph does not fit in either runtime's 2 GB
default:

```bash
colima start --memory 4 --cpu 4     # Colima: a VM setting
                                    # Docker Desktop: Settings -> Resources
```

Mounting `csv/` when you start the container is the least fiddly route, and
takes 13 seconds:

```bash
cd fraud_1_1m
docker run -d --name memgraph-mage -p 7687:7687 -p 7444:7444 \
  -v "$(pwd)/csv:/csv:ro" memgraph/memgraph-mage:latest
docker exec -i memgraph-mage mgconsole < load_memgraph.cypher
```

On Colima the clone must sit **under your home directory**: only `/Users/<you>`
is passed into the VM, and mounting anything else gives an empty directory with
no error, so the load silently creates nothing.

For a container that is already running, copy the files in instead (18
seconds) — a mount cannot be added to a live container:

```bash
cd fraud_1_1m
docker exec -u root memgraph-mage rm -rf /csv   # docker cp nests otherwise
docker cp csv memgraph-mage:/csv
docker exec -i memgraph-mage mgconsole < load_memgraph.cypher
```

Both quirks are worth knowing: `docker cp csv container:/csv` creates
`/csv/csv` if `/csv` exists, and the container user cannot delete root-owned
files there. A stale `/csv` is the one mistake here that yields wrong data
instead of an error.

**Not in a container?** The script reads from `/csv/`, so repoint it:

```bash
sed -i '' "s|/csv/|$(pwd)/csv/|g" load_memgraph.cypher   # macOS; drop the '' on Linux
mgconsole < load_memgraph.cypher
```

`load_memgraph.cypher` creates the indexes, bulk loads in
`IN_MEMORY_ANALYTICAL`, then returns to `IN_MEMORY_TRANSACTIONAL` and adds the
seven uniqueness constraints — analytical mode rejects constraints, which is
also why the mode switch fails if constraints from an earlier load still exist:

```cypher
DROP CONSTRAINT ON (n:Transaction) ASSERT n.id IS UNIQUE;  -- and Client, Bank,
DROP CONSTRAINT ON (n:SSN) ASSERT n.ssn IS UNIQUE;         -- Merchant, Email, Phone
STORAGE MODE IN_MEMORY_ANALYTICAL;
DROP GRAPH;
```

Transactions load one file per type because **neither engine can take a label
from a CSV column** — that is why `csv/` has five transaction files rather than
one, and MySQL reads the `type` column from those same files. `NEXT`,
`FIRST_TX` and `LAST_TX` are wired in later passes, once every transaction
exists.

Memgraph Community has a single graph, so loading this replaces whatever was
there.

### Neo4j 5.x+ / Neo4j Desktop — 40 seconds

Use `load_neo4j.cypher`. Neo4j resolves `file:///` against one specific folder,
so the CSVs have to be put there first.

**Neo4j Desktop**

1. Create a DBMS (or use an existing one) and note its password. Use an **empty**
   database — the script creates, it does not merge.
2. In Desktop, click the `...` button on the DBMS → **Open folder** → **Import**.
3. Copy the *contents* of `csv/` into that folder — the eleven `.csv` files
   themselves, not the `csv/` directory.
4. Start the DBMS, then either paste `load_neo4j.cypher` into Neo4j Browser (it
   runs one statement at a time) or, from the DBMS's `...` → **Terminal**:

```bash
bin/cypher-shell -u neo4j -p <password> -f /path/to/load_neo4j.cypher
```

**Server install**

```bash
cp csv/*.csv "$NEO4J_HOME/import/"
cypher-shell -u neo4j -p <password> -f load_neo4j.cypher
```

Unlike the Memgraph script this one creates the constraints *first* — Neo4j
keeps them during a load and the relationship passes need the indexes they
bring — and wraps every write in `CALL { ... } IN TRANSACTIONS OF 10000 ROWS`
so no pass runs as a single huge transaction. It also tests
`row.next_transaction_id IS NOT NULL` where the Memgraph script compares
against `""`, because Neo4j's `LOAD CSV` turns empty fields into nulls while
Memgraph's hands back empty strings.

Measured at 40 seconds for the full 1.1M nodes on a laptop — slower than
Memgraph's 18 because this builds the graph transactionally, row by row, where
Memgraph bulk loads in analytical mode.

**Why there is no `.dump` here.** Desktop can create a DBMS straight from a
dump, which is less work than the above, but a Neo4j dump only restores into a
server of the **same or newer** version than the one that wrote it. A dump of
this dataset is 297 MB and carries the kernel version of whatever Neo4j made
it, so it would fail on any older Desktop — while these CSVs are 88 MB and work
on every Neo4j from 5.0 onwards. If you want a dump for a specific Neo4j
version, load the CSVs on that version once and run
`neo4j-admin database dump <db> --to-path=<dir>`.

## Verifying a load

Both engines return the same answers.

**Fraud by type and target** — `Transfer → Client+Mule 2302`, `Payment → Merchant 656`:

```cypher
MATCH (t:Transaction)-[:TO]->(x) WHERE t.fraud
RETURN [l IN labels(t) WHERE l <> 'Transaction'][0] AS tx_type,
       CASE WHEN x:Mule THEN 'Client+Mule' WHEN x:Client THEN 'Client'
            WHEN x:Merchant THEN 'Merchant' ELSE 'Bank' END AS target,
       count(*) AS c
ORDER BY c DESC;
```

(Don't reach for `labels(t)[1]` — Neo4j and Memgraph return a node's labels in
different orders, so the same query would report a different column on each.)

```sql
SELECT t.type AS tx_type,
       CASE WHEN t.to_client_id IS NOT NULL AND c.is_mule=1 THEN 'Client+Mule'
            WHEN t.to_client_id IS NOT NULL THEN 'Client'
            WHEN t.to_merchant_id IS NOT NULL THEN 'Merchant'
            ELSE 'Bank' END AS target,
       COUNT(*) AS c
FROM transactions t LEFT JOIN clients c ON c.id = t.to_client_id
WHERE t.fraud = 1 GROUP BY tx_type, target ORDER BY c DESC;
```

**Clients one shared identity away from a mule** — `3935, 1375, 5631`. This is
where the two models diverge most: one variable-length pattern against three
UNIONed self-joins.

```cypher
MATCH (m:Mule)-[:HAS_SSN|HAS_EMAIL|HAS_PHONE]->(id)<-[:HAS_SSN|HAS_EMAIL|HAS_PHONE]-(other:Client)
WHERE other.id <> m.id
RETURN count(DISTINCT other) AS linked_clients, count(DISTINCT m) AS mules, count(*) AS paths;
```

```sql
WITH links AS (
  SELECT m.id AS mule_id, o.id AS other_id FROM clients m JOIN clients o ON o.ssn = m.ssn AND o.id <> m.id WHERE m.is_mule = 1
  UNION ALL SELECT m.id, o.id FROM clients m JOIN clients o ON o.email = m.email AND o.id <> m.id WHERE m.is_mule = 1
  UNION ALL SELECT m.id, o.id FROM clients m JOIN clients o ON o.phone_number = m.phone_number AND o.id <> m.id WHERE m.is_mule = 1
)
SELECT COUNT(DISTINCT other_id) AS linked_clients, COUNT(DISTINCT mule_id) AS mules, COUNT(*) AS paths FROM links;
```

**Referential integrity** — MySQL loads with foreign key checks off, so confirm
nothing was dropped. Every count should be 0:

```sql
SELECT 'transactions.client_id' AS fk, COUNT(*) AS orphans FROM transactions t LEFT JOIN clients c ON c.id=t.client_id WHERE c.id IS NULL
UNION ALL SELECT 'transactions.to_merchant_id', COUNT(*) FROM transactions t LEFT JOIN merchants m ON m.id=t.to_merchant_id WHERE t.to_merchant_id IS NOT NULL AND m.id IS NULL
UNION ALL SELECT 'transactions.to_client_id', COUNT(*) FROM transactions t LEFT JOIN clients c ON c.id=t.to_client_id WHERE t.to_client_id IS NOT NULL AND c.id IS NULL
UNION ALL SELECT 'transactions.to_bank_id', COUNT(*) FROM transactions t LEFT JOIN banks b ON b.id=t.to_bank_id WHERE t.to_bank_id IS NOT NULL AND b.id IS NULL
UNION ALL SELECT 'transactions.next_transaction_id', COUNT(*) FROM transactions a LEFT JOIN transactions b ON b.id=a.next_transaction_id WHERE a.next_transaction_id IS NOT NULL AND b.id IS NULL
UNION ALL SELECT 'clients.ssn', COUNT(*) FROM clients c LEFT JOIN ssns s ON s.ssn=c.ssn WHERE s.ssn IS NULL
UNION ALL SELECT 'clients.email', COUNT(*) FROM clients c LEFT JOIN emails e ON e.email=c.email WHERE e.email IS NULL
UNION ALL SELECT 'clients.phone_number', COUNT(*) FROM clients c LEFT JOIN phones p ON p.phone_number=c.phone_number WHERE p.phone_number IS NULL
UNION ALL SELECT 'clients.first_tx_id', COUNT(*) FROM clients c LEFT JOIN transactions t ON t.id=c.first_tx_id WHERE c.first_tx_id IS NOT NULL AND t.id IS NULL
UNION ALL SELECT 'clients.last_tx_id', COUNT(*) FROM clients c LEFT JOIN transactions t ON t.id=c.last_tx_id WHERE c.last_tx_id IS NOT NULL AND t.id IS NULL
UNION ALL SELECT 'exactly-one TO target', COUNT(*) FROM transactions WHERE (to_merchant_id IS NOT NULL)+(to_client_id IS NOT NULL)+(to_bank_id IS NOT NULL) <> 1;
```

## Troubleshooting

Every message below is verbatim from actually hitting the problem.

**MySQL — `ERROR 3948 (42000): Loading local data is disabled; this must be
enabled on both the client and server sides`**
The `--local-infile=1` flag covers the client only. Run
`SET GLOBAL local_infile=1;` as a privileged user, load, then set it back to 0.
If you have no such account, move `csv/` into the folder named by
`SELECT @@secure_file_priv;` and change `LOAD DATA LOCAL INFILE` to
`LOAD DATA INFILE`.

**MySQL — `ERROR 2 (HY000) at line 1: File 'csv/banks.csv' not found (OS
errno 2 - No such file or directory)`**
The loader's paths are relative. Run it from inside `fraud_1_1m/`, not from the
repo root.

**Memgraph — `Client received query exception: CSV file not found: /csv/banks.csv`**
The server cannot see the files. In a container they must be mounted at `/csv`
or copied there with `docker cp`; a native install needs the paths rewritten
(see the Memgraph section). Remember it is the *server's* filesystem that
matters, not yours.

**Memgraph — the load runs with no errors but `MATCH (n) RETURN count(n)`
returns 0 or a number from an earlier load**
Two causes, neither of which announces itself:
- On Colima, a `-v` mount of a path outside your home directory appears as an
  empty directory. Move the clone under `/Users/<you>`.
- `docker cp csv container:/csv` nests into `/csv/csv` when `/csv` already
  exists, leaving the *old* files in place. Run
  `docker exec -u root <container> rm -rf /csv` first.

**Memgraph — `rm: cannot remove '/csv/banks.csv': Permission denied`**
`docker cp` writes as root; the container's own user cannot delete those files.
Add `-u root` to the `docker exec`.

**Memgraph — `Constraints are not supported in analytical storage mode. Please
drop them before changing storage mode to analytical or use transactional
mode.`**
A previous load left its uniqueness constraints behind. Drop the seven listed
in the Memgraph section, then switch mode and `DROP GRAPH`.

**Memgraph — the container dies or the load aborts partway**
Out of memory. The graph needs 1.58 GiB and neither Colima nor Docker Desktop
gives 2 GB-plus by default: `colima start --memory 4 --cpu 4`, or Docker
Desktop → Settings → Resources.

**Neo4j — `22N43: data exception - unable to load external resource. Could not
load external resource from file:///banks.csv.`**
The CSVs are not in the database's import folder, or the `csv/` folder itself
was copied in rather than its contents. `file:///banks.csv` resolves to
`<import folder>/banks.csv`, so the eleven files must sit there loose. In
Desktop: the DBMS's `...` → **Open folder** → **Import**.

**Neo4j — `22N79: property uniqueness constraint violated. ... already exists
with label 'Bank' and property 'id' = ...`** (Neo4j 5.x words the same thing as
`Neo.ClientError.Schema.ConstraintValidationFailed`)
The database wasn't empty. The loader creates rather than merges, so run it
against a fresh one.

**Neo4j — a `.dump` you made elsewhere won't load: `not on a supported version
(current format: ...). Use the 'neo4j-admin database migrate' command`**
Dumps move forward only. Run
`neo4j-admin database migrate <db> --force-btree-indexes-to-range` after
loading an older dump; a *newer* dump cannot be restored into an older Neo4j at
all, which is why this repo ships CSVs instead.

**Any engine — counts don't match 1,100,000**
Compare against the per-label and per-table numbers in
[`fraud_1_1m/README.md`](fraud_1_1m/README.md); it also has the
referential-integrity sweep for MySQL, which loads with foreign key checks off
and so will happily accept a partial load.

two engines. Empty string means NULL / no relationship, and `fraud` / `is_mule`
are `0`/`1`.
